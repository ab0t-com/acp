            ACP: The Agent Coordination Protocol, Version 1

Abstract

   The Agent Coordination Protocol (ACP) gives two or more autonomous
   software agents -- typically AI "agent harnesses" running on different
   machines -- a shared filesystem and a communications channel so they
   can collaborate: co-author files and documents, exchange messages,
   coordinate exclusive access to resources, and observe a single ordered
   record of what happened.  ACP is a client/authority protocol over
   HTTPS: a daemon ("coordd") is the authority; agents are clients.  This
   document specifies version 1 of the protocol ("acp/1"): its transport,
   authentication and authorization, multi-tenant "spaces", the totally-
   ordered event log, the directed mailbox, fencing-token leases, the
   content-addressed shared filesystem (blobs + a CAS-versioned
   manifest), collaborative documents (a sequence CRDT), presence, the
   high-availability (Raft) clustering model, administration, the error
   model, and security considerations.

Status of This Memo

   This is a product protocol specification published for implementers
   and integrators of ACP.  It is complete and normative for "acp/1".
   Distribution is unlimited.

1.  Introduction

   Multiple autonomous agents that work together need two things they do
   not get from a bare network: a place to share files and state with a
   consistent view, and a channel to message and coordinate without
   corrupting one another's work.  Peer-to-peer file sync provides
   eventual consistency and conflict files; that is insufficient for
   questions like "did I acquire the lock?" or "what is the current task
   state?".  ACP therefore defines a single AUTHORITY that imposes a
   total order on all coordination events and mediates all shared state.

   ACP provides, per isolated "space":

   o  a content-addressed SHARED FILESYSTEM with compare-and-swap commits
      and 3-way reconciliation;
   o  COLLABORATIVE DOCUMENTS that converge automatically when many
      agents edit the same text concurrently (a sequence CRDT);
   o  a directed MAILBOX for agent-to-agent messages;
   o  a totally-ordered, durable EVENT LOG that all agents replay to
      derive shared state;
   o  fencing-token LEASES for safe mutual exclusion;
   o  PRESENCE and identity.

   The authority MAY run as a single node or as a Raft cluster for high
   availability.  Clients are unaffected by which.

   This document specifies the wire protocol, not any particular
   implementation, except where determinism (Section 17) constrains
   implementations of a cluster.

2.  Conventions and Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this
   document are to be interpreted as described in RFC 2119 and RFC 8174
   when, and only when, they appear in all capitals.

   Agent          A client participant, identified by an agent id.  An AI
                  harness (e.g., a coding agent) is the typical agent.

   Authority      The logical service that owns all coordination state.
                  Realized by one daemon ("coordd") or a cluster thereof.

   coordd         The reference daemon implementing the authority.

   Node           One process/member of an authority cluster.

   Leader         In a cluster, the node that accepts writes (Section 14).

   Space          A named, fully isolated tenant: its own event log,
                  mailbox, leases, filesystem, documents, and presence.
                  Spaces share nothing.  The default space is "default".

   Event          One immutable, sequence-numbered record in the event
                  log (Section 8).

   Seq            A strictly increasing 64-bit unsigned integer assigned
                  by the authority to each event, defining total order.

   Message        A directed mailbox item from one agent to another
                  (Section 9).

   Lease          A TTL-bounded advisory lock on a named resource, with a
                  fencing token (Section 10).

   Fencing token  A strictly increasing 64-bit unsigned integer minted on
                  each lease grant, used to reject a stale lock holder.

   Blob           An immutable byte object addressed by the SHA-256 hash
                  of its (plaintext) contents (Section 11).

   Manifest       The versioned map of logical paths to blob hashes that
                  defines a space's shared filesystem (Section 11).

   Document       A collaborative text object edited via CRDT operations
                  (Section 12).

   Op             A single CRDT mutation (insert or delete).

   Epoch          A per-document generation counter, incremented when a
                  document's operation log is compacted (Section 12).

   Write          Any request that mutates authority state.  Reads do not
                  mutate state.

3.  Architecture

   ACP is client/authority.  Agents are clients; the authority is a
   single source of truth.  Agents do not communicate peer-to-peer; they
   rendezvous through the authority, which is what makes ordering,
   locking, and audit consistent.

      machine 1                                       machine 2
   +-----------+      HTTPS (TLS, bearer token)      +-----------+
   | agent A   |<----------------------------------->| agent B   |
   | (client)  |                  |                  | (client)  |
   +-----------+         +------------------+         +-----------+
                         |   authority      |
                         |  (coordd / Raft) |
                         |  per space:      |
                         |   event log      |
                         |   mailbox        |
                         |   leases         |
                         |   blobs+manifest |
                         |   documents      |
                         |   presence       |
                         +------------------+

   The authority MUST present one logical HTTPS endpoint.  An
   implementation MAY be a single node or a cluster (Section 14); the
   client-visible protocol is identical.

   All state is partitioned by space (Section 7).  Within a space the
   authority maintains the six subsystems above.

4.  Transport

   ACP runs over HTTP/1.1 or HTTP/2 on TLS ("HTTPS").

   4.1.  TLS

   The authority MUST serve TLS 1.2 or later (TLS 1.3 RECOMMENDED).  The
   authority MAY use a self-signed certificate.  Clients SHOULD pin the
   authority's certificate (trust it as the sole root) rather than rely
   on a public CA; clients MUST NOT disable certificate verification in
   production.  The certificate's SANs MUST include the host name or IP
   the client connects to.

   4.2.  HTTP

   Requests and responses are HTTP.  JSON request and response bodies use
   media type application/json (Section 6).  Two endpoints deviate:
   blob upload/download use application/octet-stream (Section 11), and the
   event stream uses application/x-ndjson (Section 8).

5.  Authentication and Authorization

   5.1.  Bearer Token

   Every request except GET /v1/healthz MUST carry:

      Authorization: Bearer <token>

   The authority MUST validate the token and SHOULD compare it in
   constant time.  An invalid or missing token MUST yield 401.

   5.2.  Identity

   An authority operates in one of two identity modes:

   o  Shared-token mode: a single token authorizes all agents.  The
      caller's agent id is taken from the X-ACP-Agent header (Section 6),
      which is trusted in this mode.

   o  Per-agent mode: each agent has its own token mapped to an agent id
      and role.  In this mode the agent id and role MUST be DERIVED FROM
      THE TOKEN; the X-ACP-Agent header MUST be ignored for identity, so
      an agent cannot impersonate another.

   The authority MUST set the actor/originator fields of stored events
   and messages from the authenticated identity, never from client-
   supplied fields.

   5.3.  Roles

   Per-agent mode assigns each identity a role:

      admin   - all operations, including /v1/admin/*.
      writer  - reads and writes, but not /v1/admin/*.
      reader  - read-only (HTTP GET) plus the presence heartbeat
                (POST /v1/agents/beat).

   A request the role does not permit MUST yield 403.  In shared-token
   mode the caller is effectively admin.

   5.4.  Rate Limiting

   The authority MAY rate-limit per agent and MUST signal throttling with
   429 and a Retry-After header.

6.  Message Conventions (Headers, Encoding, Errors)

   6.1.  Request Headers

   Authorization     REQUIRED (except /v1/healthz).  "Bearer <token>".
   X-ACP-Agent       Agent id.  Authoritative only in shared-token mode.
   X-ACP-Protocol    OPTIONAL.  The protocol version, "acp/1".  If
                     present and not equal to the authority's version,
                     the authority MUST respond 400.
   X-ACP-Space       OPTIONAL.  The target space.  Absent means
                     "default".
   X-ACP-Session     OPTIONAL.  A random per-process identifier used for
                     presence collision detection (Section 13).
   Idempotency-Key   OPTIONAL.  Honored on POST /v1/events and
                     POST /v1/mail (Section 6.4).

   6.2.  Bodies

   Unless noted, request and response bodies are JSON (RFC 8259), UTF-8.
   Field names are lowercase snake_case.  Unknown fields SHOULD be
   ignored by receivers.

   6.3.  Errors

   Error responses use an HTTP status >= 400 and a JSON body:

      { "error": "<human-readable message>",
        "current": <optional state> }

   The "current" field carries the authority's current state for
   conflicts (e.g., the current lease holder on 409, or the current
   manifest on a version conflict) so a client can reconcile without an
   extra round trip.  Status codes are summarized in Appendix B.

   6.3.1.  When a 503 May Be Sent Again

   A 503 can mean two different things.  Sometimes the authority refused
   the request before acting on it.  Sometimes it does not know the
   outcome: a replicated write that did not commit in time can still
   commit afterwards, and sending it again would apply it twice.

   The error body gains an optional member:

      { "error": "...", "retry_safe": true }

   "retry_safe": true is a promise that the authority did not act on this
   request and will not act on it later.  An authority MUST NOT send it
   when the request may yet take effect, and MUST send it only with 503.
   The member is optional: its absence promises nothing either way, and
   an older authority never sends it.

   A client MAY then resend the request as it is, after the Retry-After
   delay.  Without the member, a client MAY resend automatically only a
   request that is safe by itself: GET, HEAD, or a write carrying an
   Idempotency-Key (Section 6.4).  Any other write MUST NOT be resent
   automatically.  A client SHOULD bound its automatic retries.  A 503
   with no Retry-After (for example code "space_unavailable") needs an
   operator, and SHOULD NOT be retried automatically.

====== END RATIFIED AMENDMENT · id=acp1-6.3-retry-safe ======

   6.4.  Idempotency

   When a client supplies Idempotency-Key on a supported write, the
   authority MUST return the original result for any repeat of that key
   and MUST NOT apply the write more than once.  A replayed response
   SHOULD carry the header "X-ACP-Idempotent-Replay: true".  Keys MAY be
   evicted after a bounded retention.

====== BEGIN RATIFIED AMENDMENT · id=acp1-6.4-idem-key-binds-request · proposed 2026-11-02 · RATIFIED (2026-11-02, owner) ======

   6.4.1.  A Key Binds Its Request

   A key stands for one request.  The authority MUST record a fingerprint
   of the request with the key's result.  A later use of the key with a
   different request MUST NOT replay and MUST NOT write: the authority
   answers 422 with code "idempotency_key_reused" and keeps the original
   result under the key, so a true retry of the original still replays.
   "Repeat" in Section 6.4 means this: same key, same request.

   The fingerprint covers what the client sent as the server understands
   it, before any server-assigned field, so whitespace, member order and
   members the server ignores do not change it.  It is recorded and
   compared in the replicated apply, so every replica reaches the same
   verdict (Section 17).  A key recorded by an authority that kept no
   fingerprint is not judged: it replays, as it did.

   Rationale: replaying the first result for a different request answered
   200 for a write that was never stored.

   Conformance: TestIdemKeyReuseWithDifferentBodyIs422,
   TestDeterministicApplyIncludesIdemFingerprint.

====== END RATIFIED AMENDMENT · id=acp1-6.4-idem-key-binds-request ======

7.  Spaces (Multi-Tenancy)

   A space is a fully isolated coordination domain.  All endpoints
   operate within the space named by X-ACP-Space (default "default").
   Spaces MUST NOT share events, messages, leases, blobs, manifests,
   documents, or presence.  Space names MUST match [A-Za-z0-9_-]+ and be
   at most 64 octets.  A space is created on first use.

   GET /v1/spaces returns the set of spaces known to the authority:

      { "spaces": ["default", "projX", ...] }

   Client-side state (e.g., a working copy's sync base) SHOULD be
   namespaced by (authority, space, agent) so one client may safely use
   many spaces and authorities without collision.

====== BEGIN RATIFIED AMENDMENT · id=acp1-7-reads-never-create · proposed 2026-11-02 · RATIFIED (2026-11-06, owner) ======
   This amendment replaces the sentence "A space is created on first
   use" above.  It tightens it: a space that used to appear on any
   request now appears only on a write.

   7.1.  How a space comes to exist.  A space is created by the first
   write that stores something in it: an event, a message, a lease, a
   blob, a commit, or a document op; or by an admin setting its mode or
   its quota, or creating an invite for it.  The space "default" always
   exists.

   A request that does not store anything MUST NOT create a space.
   That covers every GET and HEAD, the read-shaped POSTs
   (POST /v1/blobs/has, a blob capability mint), a heartbeat, and a
   write that acts on something that must already be there (a lease
   renew or release, an acknowledgement, a delete, a restore, a
   checkpoint, an admin compaction or collection).  Such a request
   leaves no state behind and MUST NOT count against any limit on the
   number of spaces.

   7.2.  The answer.  Such a request naming a space that does not exist
   gets 404 with code "space_not_found", after the checks that come
   before it: a malformed name is 400, and a space outside the token's
   space scope is 403 whether it exists or not, so that a scoped token
   learns nothing about other names.  A space the operator removed is
   a space that does not exist.  GET /v1/whoami answers as usual,
   because identity does not depend on a space.

   7.3.  Clusters.  A space exists from its first committed write, and
   a follower may not have applied it yet, so a follower MUST NOT
   answer space_not_found on its own: it asks the leader, as it does
   for a write.

   7.4.  Clients.  A client about to write to a space that may be new
   reads first as usual and treats space_not_found as an empty space
   at manifest version 0 in cas mode, then writes.  A client that is
   only reading reports it: a mistyped name must not look like an
   empty workspace.  A write to a mistyped name still creates it; a
   client MAY ask its user first.

8.  Event Log

   The event log is the per-space, append-only, totally-ordered record of
   facts.  Every cross-agent action SHOULD be reflected as an event so
   that all agents derive the same shared state from the same order.

   8.1.  Event Object

   See Appendix A.  An event has at least: seq, at (RFC 3339 UTC), actor,
   action (a namespaced string such as "file.edited", "lease.acquired",
   "chat.sent", "crdt.op", "note.added"), and OPTIONAL entity, before,
   after, and context objects.

   8.2.  Append

   POST /v1/events with a JSON object {action, entity?, before?, after?,
   context?}.  The authority MUST set actor to the authenticated
   identity, assign the next seq, set "at", durably persist the event
   before acknowledging, and return the stored event.  seq MUST be
   strictly increasing within a space and MUST persist across restarts.

   8.3.  Read

   GET /v1/events?from=<seq> returns the array of events with seq >=
   from.

   8.4.  Streaming

   GET /v1/events?from=<seq>&follow=true returns a live stream encoded as
   newline-delimited JSON (application/x-ndjson): one event object per
   line.  The authority MUST first send the backlog from "from" up to a
   snapshot point and then forward subsequent events, without gaps or
   duplicates across the cutover.  A client that is disconnected or
   dropped MUST resume by reconnecting with from set to one past the last
   seq it received; no committed event is thereby lost.

   8.5.  Compaction

   The authority MAY compact old events to bound storage.  After
   compaction, seq MUST continue to increase (only old history is
   dropped).  The lowest retained seq is the "base seq"; a client
   requesting events before the base seq receives only the retained tail.
   Compaction MUST NOT affect derived state (leases, manifest, etc.),
   which is independently durable.

====== BEGIN RATIFIED AMENDMENT · id=acp1-8.5-retention-by-kind · proposed 2026-11-02 · RATIFIED (2026-11-02, owner) ======

   8.5.1.  Retention Counted by Kind

   An authority that bounds the event log by a count of N events SHOULD
   count two kinds of event separately, so that a burst of one cannot
   evict the other:

      audit         records the authority writes as a by-product of a
                    state change (file.*, fs.*, crdt.*, crdtjson.*,
                    lease.*, checkpoint.*, manifest.*, bulk.*, history.*,
                    admin.*, blob.*, invite.*, member.*, agent.*)
      conversation  everything else: chat.sent and every action a
                    client chooses

   Compaction stays a single prefix cut: the retained events remain
   contiguous, and base seq, resume and gap detection are unchanged.  The
   cut is the latest one that leaves the newest N events of each kind in
   the retained tail, or all that kind has.  A kind with no retained event
   holds nothing back.

   An authority applying this rule MUST bound it: the events that count
   are the newest ceiling events, for a ceiling it chooses at or above N,
   so that a rare kind cannot pin the log (the reference daemon uses 4N).
   A kind with events only beyond that bound holds nothing back.  An
   authority enforcing a quota on retained events (EXT-7 max_events) MUST
   NOT let this rule hold room the quota needs: the reference daemon caps
   the tail at half the space quota, and applies no floor to a space with
   a per-label event quota.

   The decision MUST be a function of replicated state.  The authority
   chooses the first seq to keep and records it in the replicated
   command, so that every replica drops the identical prefix however many
   events landed in between (Section 17).

   Rationale: one commit of many files writes one audit event per file.
   With a single count it evicted the conversation that came before it.

   Conformance: TestEventRetentionBulkCommitKeepsTheConversation,
   TestDeterministicApplyIncludesEventCompactFromSeq.

====== BEGIN RATIFIED AMENDMENT · id=acp1-8.6-log-identity · proposed 2026-11-05 · RATIFIED (2026-11-05, owner) ======

   8.6.  Log Identity

   Seq numbers alone cannot tell a client that a space's history was
   replaced.  A server restored from a copy of its data starts again at
   an earlier head and then hands out seqs the client has already seen,
   for different events; a cluster node that is merely behind also shows
   a lower head.  The log identity tells the two apart.

   The authority gives each space's event log an identity of two parts,
   written "<space part>.<epoch>":

      space part  fixed for one life of the space's log.  It is derived
                  deterministically from the replicated command that
                  creates the log and the space name, so every replica
                  derives the same value, and it is carried in
                  snapshots.  A space that is removed and created again
                  gets a new one.  A log from before this section has
                  none: the authority derives it from the space name, or
                  reports no identity.

      epoch       random, chosen anew at every start of a single-node
                  authority and, in a cluster, by each leader once it
                  is ready after taking office.  It is replicated (a
                  command the leader proposes) and carried in snapshots;
                  a follower never chooses one.

   Every restore of an authority's data involves a start, so a restored
   history always shows a new identity.  A plain restart, and a change
   of leader, also show a new identity: the rule errs toward re-reading,
   never toward taking a restored history for the old one.

   A client compares the identity with the one it last saw:

   o  The same identity and a lower head: a node behind the others.  The
      client keeps its position and waits.

   o  A new identity: the history may have been restored or rebuilt.  A
      client that keeps derived state drops what it holds from the log,
      re-reads, and resumes at the new head.  A client that hands events
      to an application MUST NOT skip or replay events silently: it
      signals a resync carrying its old position and the new head, and
      by default re-reads.

   o  No identity: unknown (an authority without this section).  The
      client behaves as before.

====== END RATIFIED AMENDMENT · id=acp1-8.6-log-identity ======

   8.6.1.  Where the Log Identity Is Reported

   An authority that implements Section 8.6 reports the identity:

   o  in the X-ACP-Log-Id response header of GET /v1/events, and of the
      stream of Section 8.4, where it is sent before any event (the
      stream's body stays one event per line);

   o  as "log_id" in GET /v1/stats.

   It is absent while the authority has no epoch (for example a node
   that has not yet applied one, or a follower of a leader without this
   section).

   With the identity, GET /v1/events and its stream carry the
   X-ACP-Log-Head response header: the log's head when the read began.
   For the stream, it is the seq up to which the backlog is sent before
   live events follow, so a client that sees a new identity can report
   both its old position and the new head.

====== END UNSIGNED AMENDMENT · id=acp1-8.6.1-log-identity-transport ======

====== BEGIN UNSIGNED AMENDMENT · id=acp1-8.6.2-log-identity-vouched · proposed 2026-11-06 · NOT normative until ratified ======

   8.6.2.  An Identity Is Shown Only When the Node Can Vouch for It

   Restored data carries the epoch it had when it was copied.  A
   cluster node that starts on it, and a node that has not yet applied
   a newer leader's epoch, would otherwise show that epoch with a lower
   head, which reads as a node behind the others, not as a restore.

   Therefore an authority MUST NOT report an identity whose epoch it
   cannot vouch for, and reports none instead (which a client treats
   as unknown, Section 8.6):

   o  A single-node authority reports only an epoch it chose since its
      own start.

   o  A cluster node reports only an epoch chosen in its current term,
      and only once it has heard from that term's leader since it
      started.  The epoch therefore carries the term it was chosen in,
      in the replicated command and in snapshots.

   A cluster leader MUST NOT accept writes until its own epoch has been
   applied, and MUST retry choosing it until it is, for as long as it
   leads.

   (Added 2026-11-06.)  The identity is sent only when a stream opens,
   so when a node's epoch changes it MUST end every open event stream
   (Section 8.4).  A follower then reconnects and reads the new
   identity; one whose stream opened while no identity was shown learns
   it this way.  A node MUST keep its applied epoch across a restart,
   including one after a crash.

====== END UNSIGNED AMENDMENT · id=acp1-8.6.2-log-identity-vouched ======

====== BEGIN UNSIGNED AMENDMENT · id=acp1-8.6.3-log-identity-client · proposed 2026-11-06 · NOT normative until ratified ======

   8.6.3.  Following a Log by Its Identity (client rules)

   Updates: Section 8.6.  Two statements there do not hold as written.
   A restored history does not always show a new identity at once: a
   cluster node shows none until it can vouch for its epoch (Section
   8.6.2).  And "no identity" means "behave as before" only for a client
   that has never been shown one.  This section gives the client rules
   that close both gaps.  It changes nothing an authority sends.

   Terms.  A follower (an event consumer, or a client that keeps state
   derived from the log) keeps:

      position   the last seq it delivered or applied; it reopens the
                 stream at position + 1.
      identity   none, or the identity it holds, taken as below.
      mark       the seq of the last event it delivered on a stream that
                 named the held identity, and a digest of that event (or
                 the event read at its position when it took the
                 identity).  Seq 0 counts as the same event everywhere.
      behind     0, or the seq it had seen before an authority answered
                 with a lower head.

   An "event check" reads the one event at the mark's seq
   (GET /v1/events?from=<seq>&limit=1) and compares it with the mark.

   R1.  A follower holds an identity only once it is checked.  The first
        identity it is ever shown is taken as it stands.  Any later,
        different identity is taken only after an event check passes.

   R2.  The same identity with a lower head is a node that is behind.
        A stream waits at position + 1, with no gap and nothing
        replayed.  A client that serves derived state keeps what it has
        and MUST NOT serve it as current: it refuses reads until
        "behind" clears (R8).

   R3.  No identity, while the follower holds one, means "unknown".  It
        MUST NOT be read as "behave as before": nothing is decided and
        nothing is replayed, and a client that serves derived state
        refuses reads while the stream names no identity.

   R4.  A new identity: the follower runs the event check before it
        hands over any event from that stream.
        -  The same event: the same history (a restart, or a new
           leader).  It takes the new identity and goes on from
           position + 1, skipping nothing.
        -  A different event, or no event at the mark's seq (except as
           in R5): a restore.  The follower takes the new
           identity and MUST NOT go on silently: an event consumer is
           told (a resync carrying its old position and the new head) or
           stops; a client that keeps derived state drops it and reads
           everything again.

   R5.  An event check decides nothing, and the new identity is not
        taken, when it fails (a network error, a 5xx, a time limit),
        when its answer names no identity or an identity other than the
        one being checked, or when its answer holds no event at the
        mark's seq and its head is below both the mark's seq and the
        head the stream opened with.  That last answer came from a node
        behind the one the stream reached (as through a balancer that
        sends each request to any node).  An answer with no event there
        and a head at or past the head the stream opened with shows a
        shorter log: a restore (R4).  When the check decides nothing,
        the stream does not go on; the next open checks again.

   R6.  The mark moves only on events from a stream that names the held
        identity.  Events delivered on a stream that names none leave an
        unverified tail behind the mark.

   R7.  A restore (R4) clears "behind".

   R8.  "Behind" clears only on proof that the same log is back where it
        was: an event at or past the behind seq on a stream that names
        the held identity, an open that names it with a head at or past
        that seq, an event check that passes with such a head, or a
        restore.  It never clears on a stream that names no identity, or
        on a new identity not yet checked.

   R9.  The "from" of a gap reported to an event consumer is the first
        seq that may differ: position + 1, or the mark's seq + 1 when
        there is an unverified tail.

   R10. After a stream that was healthy ends (an authority ends every
        stream when its epoch changes, Section 8.6.2), the follower
        reconnects after a random wait (jitter), so that every client of
        a node does not return at the same instant; after failures it
        backs off.  Two identities that alternate MUST NOT make a client
        loop without waiting.

   R11. Against an authority that never names an identity, the follower
        keeps the rule from before Section 8.6: a lower head is told as
        "behind", and nothing more can be known.

10. Leases

   A lease is a TTL-bounded advisory lock on a named resource, used to
   serialize access (e.g., to a hot file) when OS file locks are not
   trustworthy across machines.

   10.1.  Fencing Tokens

   Each grant mints a strictly increasing fencing token.  A holder
   presents its token on protected operations; the authority MUST reject
   any token lower than the resource's current token.  This defeats the
   "expired lock, but the old holder is still running" hazard: a stale
   holder always carries a lower token and loses.

   10.2.  Acquire

   POST /v1/lease/acquire {resource, ttl_sec}.  If the resource is free
   or its lease has expired, the authority mints a NEW token and grants
   it.  If the caller already holds a live lease, it is renewed and the
   token preserved.  If another agent holds a live lease, the authority
   MUST respond 409 with the current lease in "current".  ttl_sec
   defaults to 300 if not positive.

   10.3.  Renew / Release

   POST /v1/lease/renew {resource, token, ttl_sec} extends a lease the
   caller holds (matched by token); otherwise 409.  POST
   /v1/lease/release {resource, token} frees it; mismatch yields 409.

   10.4.  List and Expiry

   GET /v1/lease lists live leases.  The authority MUST expire leases
   whose TTL has elapsed and SHOULD record expiry as a "lease.expired"
   event so other agents learn the resource is free.

   10.5.  Enforcement on Commit

   When lease enforcement is enabled, a commit (Section 11) to a path
   over which another agent holds the lease named "file:<path>" MUST be
   rejected with 423 (Locked), with the holding lease in "current".

11. Shared Filesystem: Blobs and Manifest

   The shared filesystem is content-addressed.  File CONTENTS are stored
   as immutable blobs keyed by the SHA-256 of the plaintext.  A versioned
   MANIFEST maps logical paths to blob hashes; a space's filesystem state
   is exactly (manifest version + referenced blobs).

   11.1.  Blobs

   POST /v1/blobs with a raw octet-stream body stores the content and
   returns {hash, size}.  Storage MUST be idempotent: re-putting
   identical content is a no-op returning the same hash.  GET
   /v1/blobs/<hash> returns the bytes (404 if absent).  POST
   /v1/blobs/has {hashes:[...]} returns {missing:[...]}, the subset not
   present, so a client can upload only what is needed.

   The "hash" MUST be the SHA-256 of the PLAINTEXT content even when the
   authority encrypts blobs at rest (Section 19), so deduplication,
   integrity, and manifest references are unaffected by encryption.

   11.2.  Manifest

   GET /v1/manifest returns {version, entries}, where entries maps each
   path to {path, hash, size, mtime}.  version is a per-space monotonic
   integer starting at 0.

   11.3.  Commit (Compare-and-Swap)

   POST /v1/commit with {base_version, changes, note?}, where each change
   is {path, hash?, size?, deleted?}.  The authority MUST apply the
   changes atomically if and only if base_version equals the current
   manifest version (CAS).  On mismatch it MUST respond 409 with the
   current manifest in "current"; the client rebases and retries.  All
   referenced blobs MUST already be uploaded; a missing blob yields 400.
   Paths MUST be validated (Section 11.4); an illegal path yields 400.
   If a path is leased by another agent and enforcement is on, the
   authority MUST respond 423 (Section 10.5).  On success the authority
   increments the version, returns the new manifest, and SHOULD append a
   "file.edited" or "file.deleted" event per change.

   Two agents committing changes to DIFFERENT paths do not conflict (CAS
   serializes commits but both succeed in turn).  Concurrent commits to
   the SAME path are resolved by CAS + client-side 3-way reconciliation,
   or prevented by a lease.

   11.4.  Path Validation

   The authority MUST reject any commit path that is empty, absolute,
   non-canonical, contains a "." or ".." segment, or contains a
   backslash.  This prevents a malicious or buggy client from causing any
   peer's materialization to escape its workspace directory.

   11.4.1.  A Path Is a File or a Folder

   A manifest MUST NOT come to hold one path as both a file and a folder:
   "a" beside "a/b" has no form on any filesystem, so every later
   materialization of that manifest fails.  The authority MUST refuse a

   folder of another entry, or would have another entry as a prefix

   Only created paths are judged, so a manifest that already holds such a
   pair stays repairable: a commit that does not create a colliding path
   MUST NOT be refused for it.  A restore of a retained version (EXT-33)
   is not judged either: it returns to a state the space really held.

   The refusal is a function of the commit and the manifest, so every
   replica reaches it (Section 17).

   Rationale: the commit used to succeed, and the damage showed up later,
   on every peer, as a failed pull.

12. Collaborative Documents (CRDT)

   Documents allow many agents to edit the SAME text concurrently with
   automatic, conflict-free convergence, complementing the coarser file
   commit path.

   12.1.  Model

   A document is an ordered sequence of elements, each an immutable
   character with a globally unique identifier id = (clock, replica),
   where clock is a Lamport-style counter and replica is the originating
   agent.  An insert records the id of the element it follows
   ("origin_left"; the document start is the zero id).  A delete
   tombstones an element by id.  Operations MUST be COMMUTATIVE and
   IDEMPOTENT: applying the same set of operations in any order, any
   number of times, yields the same document.  Integration of a new
   element compares origin positions first, then id, which is convergent
   for concurrent inserts (the rule underlying RGA/YATA-class CRDTs).

   A replica name belongs to exactly one agent: the agent whose id it
   equals, or whose id followed by "/" is a prefix of it (for example
   agent "bob" owns "bob" and "bob/laptop", but not "bobby" or

   contains an insert whose id names a replica the caller does not
   own, without applying any op of that push.  A delete MAY name
   another agent's replica when the element already exists (deleting a
   teammate's text is normal collaboration); a delete of an id under
   another agent's replica that the document does not hold MUST be

   the client is told of the drop is the subject of Section 12.3.1.

   clients but cannot stop a token holder that claims another agent's

   12.2.  Operation Object

   An Op is { "t": "ins" | "del", "id": {"c":<uint>,"r":<string>},
   "o": {"c","r"} (origin, inserts only), "v": "<single character>"
   (inserts only) }.

   12.3.  Push Operations

   POST /v1/crdt/ops {doc, ops, epoch?}.  The authority appends the
   operations durably and returns {doc, total, epoch}, where total is the
   document's operation count.  If "epoch" is present and does not match
   the document's current epoch, the authority MUST respond 409 (the
   document was compacted; the client MUST resync, Section 12.5).  Pushes
   SHOULD also append a "crdt.op" event so watchers notice activity.

   12.4.  Pull Operations and Materialization

   GET /v1/crdt/ops?doc=<name>&from=<index> returns {doc, ops, total,
   epoch}: operations with index >= from.  Because operations commute,
   the cursor "from" is the only synchronization state a client needs.
   GET /v1/crdt/doc?doc=<name> returns the authority-materialized text
   {doc, text, total}.  GET /v1/crdt/list returns [{name, ops, size}].

   12.5.  Compaction and the Epoch Barrier

   The authority MAY compact a document's operation log by replacing it
   with a minimal snapshot that reproduces the current visible text
   (tombstones garbage-collected, live elements re-anchored), preserving
   element ids.  Compaction MUST increment the document's epoch.  To make
   tombstone collection safe, the authority MUST reject a push whose
   epoch is behind (Section 12.3); the client then resyncs from the
   snapshot before pushing again, so it can never reference a collected
   element.

   12.5.1.  Deleting a Document; the Document Trash

   12.5.2.  The Text-Document Undo Window

   Compaction collects tombstones, which used to remove every way back
   to deleted text.  Before a compaction that would drop operations from
   a text document, the authority MUST keep the document's operation log
   as a RETAINED VERSION, identified by the document's name and the
   epoch it had before the compaction, for the space's history retention
   window (EXT-33 history_ttl_sec).  A space with that window set to 0
   keeps no versions.  A compaction that drops nothing keeps nothing.
   Operations carry no timestamp, so the window applies to whole
   versions, not to individual operations.

      GET /v1/crdt/versions?doc=<name>
          (reader) {doc, versions: [{doc, epoch, compacted_at,
          expires_at, ops}]}, oldest first
      GET /v1/crdt/versions?doc=<name>&epoch=<e>[&at=<n>]
          (reader) {doc, epoch, at, ops, text}: the text after the first
          <n> operations of that version (default: all); 404
          "version_not_found"

   A document outside the caller's read scope answers exactly as one
   with no versions.  Restoring is an ordinary edit: read the old text
   and write it back.  The authority MAY bound the versions it keeps
   (the reference daemon keeps the newest 16 per document and 1000 per
   space, so a very busy document's window can be shorter than the
   retention window) and MUST drop a version once the window has passed.
   Versions never count toward the document quota and are never
   themselves compacted.  What is kept, its name and its expiry MUST be
   a function of replicated state and the command's leader-assigned time
   (Section 17).  Structured documents (EXT-5) are not covered.

   12.6.  Client Sync Procedure (Informative)

   To merge local edits with remote ones without reverting peers, a
   client SHOULD: (1) derive local operations by diffing its file against
   its last-synced base; (2) push them; (3) pull and apply remote
   operations; (4) write the converged text back.  Deriving local edits
   MUST occur before applying remote operations.

14. High Availability (Clustering)

   An authority MAY be a Raft cluster of an odd number of nodes (3
   RECOMMENDED) to remove the single point of failure.

   14.1.  Replication

   Every WRITE is encoded as a command, appended to the Raft log,
   replicated to a majority, and then applied to the per-space state by a
   replicated state machine on every node.  A write committed by a
   majority MUST NOT be lost across a leader change.

   14.2.  Leader and Forwarding

   Only the leader applies writes.  A follower that receives a write MUST
   forward it to the leader (transparently proxying), or redirect the
   client.  Reads MAY be served by any node and are then permitted to be
   slightly stale; clients needing linearizable reads SHOULD target the
   leader.  GET /v1/cluster/status returns {mode, state, leader,
   is_leader, members}.

   14.3.  Membership

   POST /v1/admin/cluster/join {node_id, raft_addr} adds a voter; it MUST
   be processed by (or forwarded to) the leader.  Snapshots are used to
   bootstrap new or lagging nodes; restoring a snapshot MUST reset state
   so that no command is applied twice.

   14.4.  Inter-Node Security

   When a cluster CA is configured, the Raft transport MUST be mutually
   authenticated and encrypted (mTLS) using node certificates issued by
   that CA.  Absent a CA, inter-node traffic is unauthenticated and MUST
   run on a trusted private network.

   14.4.1.  Inter-Node Channel Coverage

   The mutual-authentication requirement of Section 14.4 applies to EVERY
   channel between authority nodes, not only the Raft transport: any
   node-to-node HTTP control traffic -- leader write-forwarding and
   membership join/handshake -- MUST likewise be mutually authenticated
   against the cluster CA when one is configured, and absent a CA MUST run
   only on the trusted private network.  An authority that multiplexes
   node-to-node HTTP onto a port also serving external clients MUST NOT
   weaken the external client's transport to do so: external clients
   continue to receive the daemon's client-pinned certificate unchanged
   (Section 4.1), while node peers are served a cluster-CA certificate and
   are required to present a cluster-CA client certificate.  (A
   reserved-SNI selector on the shared listener is one conforming
   mechanism; the normative requirement is that every inter-node channel
   is mutually authenticated and no external channel is weakened.)

   [This subsection was added 2026-07-27 as a clarifying amendment to
   Section 14.4; it tightens, and does not relax, the existing
   requirement, and introduces no change to the "acp/1" wire format.]

   14.5.  Single-Node

   An authority MAY run as a single node; writes are then applied
   directly.  The client-visible protocol is identical to the clustered
   case.

     2026-09-11, EXT-33 Manifest History, Retention and GC-Pin) per the

   15.1.  Garbage-Collection Reachability with Retained History

   An authority that retains historical manifest versions (EXT-33)
   MUST compute blob reachability for POST /v1/admin/gc as the union of
   the blob hashes referenced by:

      (a) the current manifest, AND
      (b) every RETAINED historical version record (those the space's
          retention policy has not evicted), AND
      (c) every version record pinned by a live checkpoint.

   A blob reachable under (a), (b) or (c) MUST NOT be reclaimed.  The
   grace window (grace_sec) continues to apply to unreachable blobs
   exactly as before.  The reachability set MUST be derived solely from
   replicated state (Section 17); the eviction of a historical record
   (which can make a blob unreachable) MUST itself be a replicated,
   leader-driven command and MUST NOT be performed inside the GC sweep.

   Event-log compaction (Section 8.5) MUST NOT remove historical version
   records; they are derived state that is independently durable, in the
   same sense as the manifest and leases.

   An authority that does not implement EXT-33 has no retained records
   and no checkpoints; for it, (b) and (c) are empty and this rule
   reduces to the existing text of Section 15.
====== END RATIFIED AMENDMENT · id=acp1-15-gc-retained-history ======

   15.2.  Garbage-Collection Reachability for a Realtime Directory Tree

   For a space (or path region) that HAS an EXT-28 CRDT directory tree in
   replicated state -- whether the region is CURRENTLY in realtime mode,
   OR retains a pre-flip realtime tree and trash from a prior EXT-31
   realtime->cas flip that is still within its retention window -- an
   authority MUST compute blob reachability for POST /v1/admin/gc as the
   union of the blob hashes referenced by:

      (a) every LIVE node of the tree (reachable from ROOT without
          passing through TRASH), AND
      (b) every RETAINED trashed node (those the space's retention policy
          has NOT evicted -- i.e. still PRESENT in replicated state;
          eviction is solely via EXT-28 fs.prune), AND
      (c) every node pinned by a live checkpoint (EXT-33).

   A blob reachable under (a), (b) or (c) MUST NOT be reclaimed.  The
   grace window (grace_sec) continues to apply to unreachable blobs
   exactly as before.  The reachability set MUST be derived solely from
   PRESENCE in replicated state (Section 17); an authority MUST NOT key
   reachability on a re-read of a node's age or on any clock.  The
   eviction of a retained trashed node -- which can make a blob
   unreachable -- MUST be a replicated, leader-driven command (EXT-28
   fs.prune) and MUST NOT be performed inside the GC sweep.  A file node
   whose content is a live CRDT document (Section 12) is reachable
   through that document's own reachability, unchanged.

   Because reachability keys on the PRESENCE of the retained realtime
   tree/trash and NOT on the region's current mode, a realtime->cas flip
   (EXT-31) does NOT narrow this reachability: a region's retained
   pre-flip trash stays pinned for the remainder of its EXT-28 retention
   window, and is evicted only by fs.prune, exactly as before the flip.

   A space that has NEVER had a realtime tree (a CAS-only space with no
   retained pre-flip realtime structure) has empty (a),(b),(c); this rule
   does not apply to it (Section 15 and amendment acp1-15-gc-retained-
   history govern).

17. Determinism Requirements

   A clustered authority's replicated state machine MUST be
   deterministic: applying the same ordered command stream MUST yield
   byte-identical state on every node.  Therefore implementations MUST
   NOT read wall-clock time, randomness, or other non-deterministic
   inputs while APPLYING a command.  All such inputs (timestamps, message
   ids, generated ids) MUST be fixed by the leader and carried in the
   command.  Background activity that mutates state (lease expiry sweeps,
   compaction) MUST also flow through the replicated log, driven by the
   leader.  Conformance SHOULD be verified by applying an identical
   command stream to independent state machines and comparing results.

   The prohibited "other non-deterministic inputs" explicitly INCLUDE any
   NODE-LOCAL state: the local filesystem's contents or layout, storage-
   engine or runtime metrics and statistics, per-node counters, process or
   environment variables, and host state.  While APPLYING a command an
   implementation MUST derive the command's effect solely from the
   replicated command and the already-replicated state; a value that can
   differ between two correct nodes applying the same command stream (a
   local metric, a directory listing, an engine's internal counter) MUST
   NOT influence the applied result.  Such values MAY be read OUTSIDE the
   apply path (for example to serve /v1/stats or an operational metric) but
   MUST NOT change replicated state.

18. Versioning and Compatibility

   The protocol version is "acp/1".  Clients MAY send X-ACP-Protocol; the
   authority MUST reject a mismatched explicit version with 400.
   Additive changes (new endpoints, new optional fields) preserve the
   version.  A breaking change MUST increment the version.  Receivers
   MUST ignore unknown JSON fields to permit additive evolution.

19. Security Considerations

   o  Transport: TLS protects confidentiality and integrity in transit;
      certificate pinning authenticates the authority and removes the
      MITM window (Section 4.1).

   o  Authentication: bearer tokens gate all non-health endpoints; tokens
      SHOULD be high-entropy (>= 128 bits) and compared in constant time.

   o  Identity integrity: in per-agent mode, identity and role derive
      from the token, so X-ACP-Agent cannot be spoofed; the authority
      sets actor/from server-side (Section 5.2).

   o  Authorization: roles gate writes and administration (Section 5.3).

   o  Tenant isolation: spaces share no state (Section 7).

   o  Input safety: commit paths and document/space names are validated
      to prevent traversal (Section 11.4).

   o  Concurrency safety: fencing-token leases (Section 10.1) and CAS
      commits (Section 11.3) and the CRDT epoch barrier (Section 12.5)
      prevent silent lost updates and stale-holder corruption.

   o  Abuse: request body size limits and per-agent rate limiting
      (Section 5.4) mitigate denial of service; idempotency keys
      (Section 6.4) make retries safe.

   o  Encryption at rest: blob contents MAY be encrypted with an
      authenticated cipher (e.g., AES-256-GCM) under an operator key;
      blobs remain keyed by plaintext hash; a wrong key MUST fail closed.
      Metadata and replicated logs not covered by application-layer
      encryption SHOULD reside on an encrypted volume.

   o  Inter-node: cluster traffic SHOULD use mTLS (Section 14.4); absent
      that, run nodes on a trusted private network.

   o  Residual risks: the audit/event log is append-only but not, in
      this version, tamper-evident; a host-level attacker with the
      authority's keys is outside the model.  Operators MUST protect the
      authority host and its key material.

Appendix B.  Error Catalog

   200  OK.
   400  Bad request: malformed body, illegal path, protocol mismatch,
        missing required field, or a referenced blob not uploaded.
   401  Unauthorized: missing or invalid bearer token.
   403  Forbidden: the caller's role does not permit the operation.
   404  Not found: unknown blob; ack of a message not addressed to the
        caller.
   405  Method not allowed.
   409  Conflict: lease held by another agent; lease renew/release token
        mismatch; manifest version conflict; CRDT epoch changed.  The
        body's "current" carries the conflicting state.
   423  Locked: commit to a path leased by another agent.
   429  Too Many Requests: rate limited; see Retry-After.
   500  Internal error.


Appendix C.  Worked Examples

   C.1.  Append and read an event (default space)

      > POST /v1/events
      > Authorization: Bearer <tok>
      > X-ACP-Agent: claudeA
      > {"action":"note.added","entity":"spec.md","context":{"n":1}}

      < 200 OK
      < {"seq":42,"at":"2026-06-10T00:00:00Z","actor":"claudeA",
      <  "action":"note.added","entity":"spec.md","context":{"n":1}}

   C.2.  Acquire a lease, then commit under it

      > POST /v1/lease/acquire {"resource":"file:app.go","ttl_sec":600}
      < 200 {"resource":"file:app.go","holder":"claudeA","token":7,...}

      A different agent committing app.go now receives:
      < 423 {"error":"path leased by claudeA: app.go","current":{...}}

   C.3.  Commit with CAS

      > POST /v1/commit
      > {"base_version":3,"changes":[{"path":"a.txt","hash":"<h>","size":9}]}
      < 200 {"version":4,"entries":{...}}            (success)
      < 409 {"error":"manifest version conflict ...","current":{...}}

   C.4.  CRDT push across a compaction boundary

      > POST /v1/crdt/ops {"doc":"spec","ops":[...],"epoch":0}
      < 409 {"error":"epoch changed - resync the doc","current":1}
      (client re-pulls from index 0 at epoch 1, re-derives, re-pushes)

   C.5.  Selecting a space

      Add "X-ACP-Space: projX" to any request to operate in space projX;
      its events, files, mail, leases, and documents are isolated from
      every other space.
